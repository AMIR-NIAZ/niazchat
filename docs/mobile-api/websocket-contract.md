# WebSocket contract (source of truth)

Applies after the 2026-11 standardization. Socket.IO v4, no namespace, origin = API origin (`PORT`). Version on the wire: all ids are **numbers** (backend bigint columns are serialized to numbers in WS payloads by `ws-serializer.utils.ts`); timestamps are ISO strings.

## Connection & auth

- Handshake: `io(BASE_URL, { transports: ['websocket'], extraHeaders: { authorization: 'Bearer <accessToken>' } })`. The `auth: { token }` baggage field is accepted but unused server-side.
- **Connection middleware (all gateways share one io server):** the access token is verified at handshake; an invalid/expired token fails the handshake → `connect_error` with `"token in valid"`. The user socket then joins its personal room `user:<userId>`; `isOnline/lastSeen` bookkeeping runs in `UserGateway`.
- **Per-event guard `wsPayload`** re-verifies the same header on every event (defense in depth).
- Rooms: `user:<id>` (personal, joined automatically at connect) and `chat:<id>` (joined via `joinChat`, left via `leaveChat`/`joinChat` of another chat/disconnect).

## Standard request/response pattern

Every client→server **request** event acks exactly once, as the ack callback's **first argument**:

```ts
// success
{ ok: true, data?: T }
// failure (produced by WsExceptionFilter from guards, pipes or handlers)
{ ok: false, message: string, status: number }
```

Never a raw `exception` event unless the caller omitted an ack callback. Guard/pipe/handler errors use the same shape. Client code: one `request<T>(event, payload)` helper with a single timeout; rejection on `ok:false`, timeout, or missing ack.

## Client behavior rules

- **History source:** the `getMessages` ack (with `joinChat`'s ack = chat info). The page is newest-first within itself; `nextCursor` is the id of its oldest message (null for an empty page). Older pages: request again with `beforeId = nextCursor` until `hasMore = false`. The app keeps the cache ascending and merges pages by id. The compat `getMessages` emit is ignored (and currently not sent).
- **Send confirmation:** the `sendMessage:list` echo replaces the optimistic pending bubble. Matching prefers `clientMessageId` (any bubble status; works for empty captions and two identical photos) and falls back to sender + trimmed content only when the echo has no `clientMessageId` (older messages). Ack failure or timeout flips the bubble to failed/retryable with the server message. The `sendMessage` ack `data` is merged by id as well.
- **Room follows focus, not mount:** the backend keeps ONE active chat room per socket (`joinChat` leaves the previous room). React Navigation keeps a chat screen mounted when another screen is pushed on top, so the app leaves the room on blur and re-joins it on focus (`active-room.ts`, `useChatMessages.ensureActive`), merging one fresh history page and `othersLastSeenId`. Without this, the screen the user returns to is no longer in `chat:<id>`, never receives the peer's messages/`seen` broadcasts, and no read receipt can be produced for them. The first focus is skipped (the conversation query's `joinChat` owns that join); a reconnect re-joins only the focused chat. The active-room marker is cleared on every socket disconnect because room membership is per connection.
- **Reconnect:** socket.io-client auto-reconnects onto a (possibly re-authenticated) handshake with backoff + jitter; the focused chat re-`joinChat`s and refetches history, and the chat list refetches on every (re)connect after the first. Every listener is bound through `useSocketEvent`, which keeps the handler in a ref and moves the subscription to a replaced instance — no listener stays on a dead socket and none duplicates.
- **Heartbeat / token expiry:** the server pings every 10 s and drops a socket that does not answer within 8 s. At 5 s before the handshake token's `exp` it emits `auth:expired` (client refreshes through the single-flight `refreshSession()` and reconnects with the new token); if the socket is still there 5 s after that warning the server disconnects it. The app shows a small `Reconnecting…` bar once the socket has been down for more than 3 s.
- **leaveChat on unmount/blur** never breaks a leave→join of the same chat: a screen only leaves the room it currently owns, and re-joining simply rejoins the room and re-reads state.
- **Typing:** group and private chats. The sender caches its display name and chat type at `joinChat`; `userTyping` is throttled server-side to one broadcast per second per socket, `userEndTyping` is always delivered, banned/non-room members are ignored, and the gateway never throws. Clients show a 5 s safety expiry and clear the user on a live message. `membersCount` is not used by private chats.
- **Read advancement:** the app sends `markSeen { chatId, lastSeenId }` while the chat is focused and `AppState === 'active'` (debounced ~300 ms, monotonic). The target is the newest confirmed id when the list is at the bottom, otherwise the highest id among the rows currently visible — so opening on the unread divider or reading older history advances the receipt without sending a message or reacting. `joinChat`/`leaveChat` never mark read. `lastSeenId` is clamped to the chat's newest message; ids above it are accepted and clamped. A no-op acks the previous value and emits nothing. A transient failure (ack timeout/offline) is retried twice with 1.5 s/3 s backoff, and an unacknowledged position is re-armed on focus/foreground/reconnect; a server rejection is never retried.
- **Unread:** `unreadCount` from `getAllChats` is authoritative = non-own, non-deleted messages with id > the caller's stored seen id (all such messages when no row exists), capped at 100 (UI shows `99+`). Live `chatlist:updated` events carry no count; the app increments locally (unless the sender is me or that chat is being read) and resyncs on focus/reconnect. `chat:read`/`seen` reset it.

## Serialization rules

- All entity ids (`id`, `chatId`, `senderId`, `messageId`, `lastSeenId`, `replyToId`, `replyTo.id`) are numbers (`Number(bigint-string)`).
- Message payloads always carry top-level `chatId` and `senderId` plus a REDUCED `sender` (`{ id, name, username, avatars }`, avatars = current photo only), `type: { id, name }`, `attachments[]` = `{ id, originalName, mimeType, size, kind: 'image'|'video'|'voice'|'file', width?, height?, duration?, hasPoster?, waveform?, createdAt }`, and `forwardedFrom: { userId: number | null, name: string } | null` (first origin; `null` for ordinary messages). `posterPath` is never exposed. Profile endpoints still return the full `toUserResponse`. Uploads are HTTP-only; the socket message only references attachment **ids**.
- Forwarding copies the file bytes into new attachment rows/files (new ids, names and `hasPoster`), so source deletion/cleanup cannot break a copy. It emits one `sendMessage:list` per new message to `chat:<targetId>` plus `chatlist:updated` for the target's last message; failed targets emit nothing.
- Replies carry `replyToId` **and** a compact `replyTo` preview (never the full entity):

```ts
replyTo: {
  id: number,
  content: string | null,   // truncated server-side to ~200 chars; null when isDeleted
  senderId: number,
  senderName: string,
  type: 'text' | 'image' | 'video' | 'file' | 'voice' | 'ice' | string,
  attachmentsCount: number,
  attachmentKind: 'image' | 'video' | 'file' | null,
  isDeleted: boolean
} | null
```

History excludes deleted messages themselves, but a reply whose original was soft-deleted still carries `replyTo.isDeleted: true` and `content: null`. Editing a message never changes its `replyTo`; the edit echo/history re-serialize the current preview of the original.

- Chat payloads carry `id`, `type`, `title` (**always `null` for private chats**), `description` (nullable, groups), `avatars[]`, `isBan`, `createdAt`, `updatedAt`, `unreadCount` (authoritative on `getAllChats`, `0` elsewhere), `peer` (private chats only; `null` for groups) and the legacy `peerName`. `peer` = `{ id, name, username, avatars[0] | [], isOnline, lastSeen }`; never a phone. — no `lastMessage`/`members` unless explicitly loaded.
- `joinChat`'s chat info adds `myLastSeenId: number | null` (stored before this join; null = never read), `othersLastSeenId: number | null` (max read id among the other non-banned members; drives my single/double ticks; null when nobody else has read) and `membersCount: number` (one count query, ban-role rows excluded by role NAME).
- Typing payloads add `userName` (cached per socket at join; never a per-event DB lookup).
- `reaction:updated` (and the `reactMessage` ack) payloads are numeric and aggregated. One reaction per user per message; switching emoji replaces the previous one, and sending the same emoji again (or `emoji: null`) removes it:

```ts
{
  chatId: number,
  messageId: number,
  reactions: Array<{
    reactId: number,
    emoji: string,       // always the canonical string from the reacts table
    count: number
  }>,
  myReaction: string | null, // recipient-specific; null when they have none
  actor: { userId: number, emoji: string | null } // null = actor cleared their reaction
}
```

- `userIds` is never broadcast or returned on a message. The reactor-list detail
  event (`getMessageReactions`) is the only surface that names users, and it
  returns at most 100 of them, newest first, grouped by emoji.
- Message payloads carry `reactions: [{ emoji, count }]` (count descending,
  then seeded catalog order; `[]` when none) on history, send/forward echoes,
  edit echoes and the send ack. History acks additionally carry the caller's
  `myReaction`; broadcasts omit it and clients keep their cached value.
- Reaction types are the rows of `GET /react` (admin-managed, six defaults seeded at startup). Clients cache that list and use the hard-coded six only as a fallback.
